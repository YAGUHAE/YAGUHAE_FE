## 0. 전제 — 기존 문서와 충돌하는 지점

`screen-design-admin.md` §0 「왜 데스크톱이 아니라 모바일인가」는 **데스크톱 콘솔을 만들지 않는다**고 못박고 있습니다. 근거는 둘입니다.

1. 입금 확인은 은행 앱과 번갈아 보는 일이고, 두 앱 모두 폰에 있다
2. 경기 당일 출석 체크는 구장에서 폰으로 한다

**둘 다 유효하고, 이 문서는 그것을 뒤집지 않습니다.** 다만 저 근거가 덮는 범위가 A-6·A-7 두 화면이라는 점을 짚습니다. 나머지 여섯 화면은 사정이 다릅니다.

| 화면 | 모바일이 정본인가 | 근거 |
|---|---|---|
| A-6 입금 확인 | **예** | §0의 근거 그대로. 데스크톱은 "PC 인터넷뱅킹을 쓰는 어드민"을 위한 동등한 대안일 뿐 |
| A-7 출석 체크 | **예** | 구장에서 폰. 데스크톱은 사후 확인용 |
| A-4 경기 등록 | 아니오 | 프레임 1329px. 11×2 슬롯 토글 + 참가비 4종 + 기본 정보를 세로로만 훑어야 함 |
| A-2 홈 | 아니오 | 대시보드는 한눈에 보는 것이 목적인데 360dp에선 스크롤해야 함 |
| A-3 경기 목록 | 아니오 | 관리자 목록은 정렬·비교가 일이라 표 형태가 유리 |
| A-5 경기 상세 | 아니오 | 보드(선공/후공)와 예약 목록을 오가는 탭 전환이 데스크톱에선 불필요 |
| A-1 로그인 · A-8 설정 | 무관 | 폼이라 어느 쪽이든 좁은 단일 열 |

**따라서 데스크톱은 대체가 아니라 추가입니다.** 모바일 목업 A-1~A-8은 그대로 정본으로 남고, `@768`·`@1280` 프레임이 옆에 붙습니다.

> **⚠️ `screen-design-admin.md` §0은 수정이 필요합니다.** "데스크톱 콘솔은 만들지 않습니다" 문장이 이 작업과 정면으로 충돌합니다. 위 표의 취지로 고쳐 쓰거나, 이 작업을 취소하거나 둘 중 하나여야 합니다. 임의로 고치지 않고 남겨 둡니다.

## 1. 브레이크포인트

**3단계. 모바일 우선이므로 360은 브레이크포인트가 아니라 기준선입니다.**

| 이름 | 범위 | 기준 폭 | 성격 |
|---|---|---|---|
| (base) | 360 ~ 767 | **360** | 터치. 기존 목업 그대로 |
| `md` | 768 ~ 1279 | **768** | 터치 태블릿. 레이아웃은 모바일과 같고 내비게이션과 여백만 바뀜 |
| `lg` | 1280 ~ | **1280** | 포인터. 콘솔 레이아웃 |

### 왜 768과 1280인가

- **768**은 아이패드 세로 폭입니다. 여기서 레이아웃을 2열로 쪼개면 각 열이 300px대가 되어 모바일보다 좁아집니다. 그래서 `md`는 **열을 늘리는 구간이 아니라 내비게이션을 바꾸는 구간**입니다.
- **1280**은 2열 콘솔이 실제로 성립하는 최소 폭입니다. 사이드바 240 + 좌우 패딩 64 + **본문 976**. 여기서 A-6 테이블 6열이 압축 없이 들어갑니다.
- **1024를 넣지 않았습니다.** 1024 - 240(사이드바) - 64 = 720px 본문이면 테이블이 잘리거나 열을 숨겨야 합니다. 열을 숨기는 순간 "어떤 열이 덜 중요한가"를 화면마다 다시 판단해야 하고, 그 판단이 목업 수를 두 배로 만듭니다. 1024~1279는 `md`로 흡수하고 중앙 정렬 단일 열로 둡니다.

### 코드

Tailwind v4 기본 브레이크포인트(`sm` 640 · `lg` 1024 · `xl` 1280 · `2xl` 1536)가 남아 있으면 `lg:`가 1024를 가리켜 이 문서와 어긋납니다. **기본값을 지우고 둘만 정의합니다.**

```css
@theme static {
  --breakpoint-*: initial;
  --breakpoint-md: 768px;
  --breakpoint-lg: 1280px;
}
```

이후 코드에서 쓰는 접두사는 `md:`와 `lg:` 둘뿐입니다. 세 번째가 나오면 이 문서를 먼저 고치세요.

## 2. 컨테이너 · 그리드

| 구간 | 좌우 패딩 | 본문 최대폭 | 내비게이션 |
|---|---|---|---|
| base | `spacing/lg` 16 | 없음 (full) | `BottomNav` 하단 고정 |
| `md` | `spacing/2xl` 24 | **640** 중앙 정렬 | `SideNav Size=Rail` 좌측 72 고정 |
| `lg` | `spacing/3xl` 32 | **1440** (콘솔 전체) | `SideNav Size=Full` 좌측 240 고정 |

`lg`의 본문 열은 사이드바를 뺀 나머지를 채웁니다: **1280 − 240 = 1040, 패딩 64를 빼면 본문 976**. 이 976이 `TableHeader`·`TableRow`의 기준 폭이고 열 폭 합계와 정확히 일치합니다. 1440을 넘는 화면에서는 콘솔 전체가 1440으로 잠기고 좌우가 비며, 사이드바는 콘텐츠 블록에 붙어 함께 중앙 정렬됩니다 — 사이드바만 뷰포트 왼쪽 끝에 붙으면 2560px 모니터에서 본문과 사이드바 사이가 어색하게 벌어집니다.

### 2열 분할 비율 (`lg` 전용)

콘솔에서 쓰는 분할은 **두 가지뿐**입니다. 화면마다 새 비율을 만들면 열 경계가 화면 간에 어긋나 보입니다.

| 이름 | 비율 | 쓰는 곳 |
|---|---|---|
| `split-even` | 1 : 1 (`gap` 32) | A-5 포지션 보드(선공/후공), A-7 출석(선공/후공) |
| `split-side` | 5 : 3 (`gap` 32) | A-2 홈, A-4 등록, A-5 상세(보드 : 예약 목록) |

## 3. 내비게이션 전환

**이 작업에서 구조적으로 가장 큰 변화입니다.** 하단 탭은 폰 전용 관용구이고, 1280px 화면 하단에 고정된 3탭 바는 어디에도 존재하지 않는 물건입니다.

```
base(360)              md(768)                 lg(1280)
┌──────────────┐      ┌──┬──────────────┐     ┌──────┬─────────────────┐
│              │      │  │              │     │ 야구해 │                 │
│   콘텐츠      │      │▣ │   콘텐츠      │     │      │                 │
│              │      │▤ │   (max 640)  │     │ ▣ 경기 │    콘텐츠        │
│              │      │▥ │              │     │ ▤ 입금 확인 ③           │
├──────────────┤      │  │              │     │ ▥ 리그 │                 │
│ ▣  ▤  ▥      │      │  │              │     │      │                 │
└──────────────┘      └──┴──────────────┘     └──────┴─────────────────┘
 BottomNav 3탭         SideNav Rail 72         SideNav Full 240
```

- **레일(72)에는 라벨이 없습니다.** 아이콘 24 + 상하 패딩으로 56px 타깃을 만들고 툴팁 없이 둡니다. 3탭뿐이고 아이콘(`calendar`·`banknote`·`users`)이 이미 명세에 고정돼 있어 라벨 없이도 식별됩니다.
- **미처리 건수 배지는 세 형태 모두에 있습니다.** `screen-design-admin.md` §0의 하단 탭 근거("앱을 열자마자 보이게")가 데스크톱에서도 그대로 유효합니다. 레일에서는 아이콘 우상단 점+숫자, 풀에서는 행 우측 끝 pill.
- **`SideNav Full` 상단에 리그명을 둡니다.** 계정이 리그에 1:1로 묶여 있으므로(§계정 모델) 지금 어느 리그를 보고 있는지가 항상 보이는 편이 낫고, 모바일 A-2 헤더에만 있던 정보가 데스크톱에선 전 화면에 상주하게 됩니다.
- **A-1 로그인에는 내비게이션이 없습니다.** 인증 전이라 사이드바를 그릴 근거가 없고, `md`·`lg` 모두 중앙 카드 하나입니다.

## 4. 신규 토큰

### Dimension (Value 모드) — 8개

| 변수 | 값 | 용도 |
|---|---|---|
| `breakpoint/md` | 768 | 문서·코드 동기화용. Figma에서는 프레임 폭 검증에만 씀 |
| `breakpoint/lg` | 1280 | 동상 |
| `size/container-content` | 640 | `md` 본문 최대폭 |
| `size/container-console` | 1440 | `lg` 콘솔 최대폭 |
| `size/sidenav-rail` | 72 | `SideNav Size=Rail` |
| `size/sidenav-full` | 240 | `SideNav Size=Full` |
| `size/topnav-height` | 64 | 용병 `lg` 상단 내비(§7). 지금은 정의만 |
| `spacing/6xl` | 64 | 콘솔 섹션 간격. 기존 최대가 `5xl` 48이라 데스크톱 여백이 부족 |

### Color (Light / Dark 모드) — 1개

| 변수 | Light | Dark | 사유 |
|---|---|---|---|
| `bg/hover` | `gray/50` | `gray/700` | **데스크톱에서 처음으로 hover가 존재합니다.** 테이블 행·사이드바 항목·목록 행에 씁니다 |

`bg/hover`가 기존 토큰의 별칭이 아닌 이유: `bg/subtle`은 `gray/50`/`gray/900`, `bg/muted`는 `gray/100`/`gray/700`입니다. 필요한 쌍(`gray/50`/`gray/700`)은 어느 쪽과도 일치하지 않습니다. `bg/default` 위에 얹혔을 때 라이트는 한 단계 어두워지고 다크는 한 단계 밝아져야 하는데, 두 모드의 방향이 반대라서 그렇습니다.

**포커스 링은 새로 만들지 않습니다.** `border/focus`와 전역 `:focus-visible` 규칙이 `globals.css:436`에 이미 있습니다. 데스크톱은 키보드 내비게이션이 실제로 쓰이는 첫 환경이므로, 신규 컴포넌트 전부에 이 규칙이 걸리는지만 확인하면 됩니다.

**44px 터치 타깃 규칙은 전 구간 유지합니다.** 포인터가 정밀해졌다고 낮추면 같은 컴포넌트가 브레이크포인트마다 다른 높이를 갖게 되고, 그 순간 컴포넌트 하나가 목업에서 둘로 갈라집니다. 실제 값은 `SideNav` Rail 항목 56 · Full 항목 44 · `TableRow` 64로 전부 44 이상입니다.

### 대비 실측 (Light / Dark)

신규 조합 전부를 WCAG AA(4.5:1) 기준으로 측정했습니다.

| 쓰이는 곳 | 조합 | Light | Dark | |
|---|---|---|---|---|
| `TableRow` Hover 이름 | `text/default` / `bg/hover` | 16.84 | 10.27 | ✅ |
| `TableRow` Hover 보조·상태문구 | `text/secondary` / `bg/hover` | 7.08 | 6.93 | ✅ |
| `TableRow` Selected 이름 | `text/default` / `bg/brand-subtle` | 15.86 | 14.85 | ✅ |
| `TableRow` Selected 보조 | `text/secondary` / `bg/brand-subtle` | 6.67 | 10.03 | ✅ |
| `SideNav` 활성 라벨 | `text/brand` / `bg/brand-subtle` | 5.86 | 6.60 | ✅ |
| `SideNav` 배지 숫자 | `text/on-brand` / `bg/brand` | 4.66 | 5.25 | ✅ |
| `SideNav` 비활성 라벨 · 섹션 헤드 | `text/secondary` / `bg/subtle` | 7.08 | 11.37 | ✅ |

## 5. 신규 컴포넌트 5종

| # | 컴포넌트 | Variant | 개수 | 사용처 |
|---|---|---|---|---|
| 25 | `SideNav` | Size(Rail/Full) × Active(Games/Payments/League) | 6 | `md`·`lg` 전 화면 (A-1 제외) |
| 26 | `PageHeader` | Actions(None/One/Two) | 3 | 콘솔 본문 최상단 — 제목 + 우측 액션 |
| 27 | `TableHeader` | — (열 라벨 TEXT × 7) | 1 | A-3 · A-6 `lg` |
| 28 | `TableRow` | State(Default/Hover/Selected) | 3 | A-3 · A-6 `lg` |
| 29 | `StatTile` | Tone(Default/Attention) | 2 | A-2 `lg` 상단 지표 |

**총 24종 → 29종, variant 95 → 110개.** 이후 용병 작업(§7.3)에서 `TopNav`(#30, Active 4변형)가 더해져 **30종 / 114개**입니다.

### `TableRow`의 상태 칸은 배타적 2택입니다

작업 중에 드러난 것입니다. **`StatusBadge`는 `ReservationStatus` enum과 1:1이라 A-3의 경기 상태(모집중·마감·취소)를 표현할 수 없습니다.** 그래서 `TableRow`의 `Cell/Status`에 `StatusText`(TEXT, 기본 숨김)를 함께 넣고 `상태 문구`·`상태 문구 표시` 프로퍼티로 갈랐습니다.

- A-6 → `StatusBadge` (승인 대기 / 입금 대기 …), `상태 표시 = true`
- A-3 → `StatusText` (모집중 / 마감 / 취소), `상태 문구 표시 = true`

경기 상태용 배지 컴포넌트를 새로 만들지 않은 이유: 모바일 `MatchRow`가 이미 pill로 그 역할을 하고 있고, 테이블 안에서는 pill보다 평문 라벨이 열 정렬을 덜 흐립니다. `StatusText`는 회색 면(Hover·Selected) 위에 올라가므로 `text/tertiary`가 아니라 `text/secondary`입니다(§4 실측).

### 만들지 않는 것

| 후보 | 뺀 이유 |
|---|---|
| `Button Size=Small` | `design-system.md` §6.2가 이미 기각한 항목입니다. 데스크톱이라고 되살릴 근거가 없습니다 |
| `Breadcrumb` | 콘솔 깊이가 2단(목록 → 상세)뿐입니다. `PageHeader`의 뒤로가기 chevron으로 충분합니다 |
| `Pagination` | 명세의 API(`GET /admin/payments?status=&gameId=&q=`)에 페이지 파라미터가 없습니다. 서버와 확정되기 전에 UI를 만들면 없는 동작을 광고하게 됩니다 → §8-2 |
| `Checkbox` / 일괄 선택 | 아래 참고 |
| `Tooltip` | 레일 아이콘 3개가 명세에 고정된 아이콘이라 식별에 문제가 없습니다. 항목이 늘면 그때 |

> **일괄 처리(`선택 N건 입금 완료`)를 넣지 않았습니다.** 데스크톱 테이블에서 가장 먼저 떠오르는 기능이고 A-6에서 실제로 유용하겠지만, 명세의 엔드포인트는 단건(`PATCH /admin/reservations/:id/confirm-payment`)입니다. `design-system.md` §6.2가 "구장 사진"·"프로모 배너"를 뺀 것과 같은 판단입니다 — **데이터·API가 없는 기능은 목업에 넣는 순간 목업이 실제보다 풍성해 보여 판단을 흐립니다.** 제품 결정이 나면 `TableRow`에 `Selectable` BOOLEAN을 추가하는 것으로 확장됩니다 → §8-1

### `TableRow`가 `MatchRow`를 대체하지 않는 이유

`MatchRow`는 base·`md`에서 계속 쓰입니다. 같은 데이터의 두 표현이고, 브레이크포인트에 따라 **컴포넌트를 통째로 교체**합니다. 하나의 컴포넌트가 폭에 따라 내부 구조를 바꾸도록 만들지 않는 이유는 Figma에 그런 장치가 없기 때문입니다 — auto-layout wrap으로 흉내 내면 열 정렬이 깨집니다. 코드에서는 `hidden lg:table-row` / `lg:hidden`으로 갈라집니다.

## 6. 화면별 설계 (A-1 ~ A-8)

`md`는 별도로 적지 않은 한 **base 레이아웃 + 640 중앙 정렬 + 레일 사이드바**입니다. 아래는 `lg` 기준입니다.

### A-1 로그인 — `lg` 640 / `md` 640

중앙 카드 **400px**. 사이드바 없음.

**좌측 브랜드 패널을 두지 않았습니다.** 로그인 화면 절반을 브랜드 이미지로 채우는 건 흔한 패턴이지만, 채울 콘텐츠가 없으면 로고를 크게 키운 빈 면이 됩니다. §6.2가 프로모 배너를 뺀 것과 같은 이유입니다. 마크 「Y」 + 워드마크 + 리그 어드민 표기를 카드 상단에 두고 끝냅니다.

### A-2 홈 — `lg` 콘솔

```
┌──────┬───────────────────────────────────────────┐
│      │ 리그명 · 2026년 9월 3일 (수)                │  PageHeader
│ ▣ 경기 ├─────────────┬─────────────┬─────────────┤
│ ▤ 입금 │ 입금 확인 대기 │ 오늘/내일 경기 │ 모집중 경기  │  StatTile × 3
│ ▥ 리그 │      3건     │     1개      │     4개     │
│      ├───────────────────────┬───────────────────┤
│      │ 다가오는 경기           │ 확인 대기 건       │  split-side (5:3)
│      │ ┌───────────────────┐ │ ┌───────────────┐ │
│      │ │ 9/6(토) 19:00     │ │ │ 김철수 34,000 │ │
│      │ │ 상암 · 4/11 6/11  │ │ ├───────────────┤ │
│      │ ├───────────────────┤ │ │ 이영희 17,000 │ │
│      │ │ 9/13(토) 19:00    │ │ ├───────────────┤ │
│      │ └───────────────────┘ │ │ 박민수  무료   │ │
│      │                       │ │ [ 전체 보기 ] │ │
└──────┴───────────────────────┴───────────────────┘
```

- **`StatTile`이 3개입니다.** 모바일은 처리 대기 카드 2개(입금 확인·오늘/내일 경기)인데, 가로가 남으므로 `모집중 경기`를 더합니다. 이건 A-3 탭에 이미 있는 수치라 새 데이터가 아닙니다.
- **`0`은 그대로 표시합니다.** 명세 §A-2의 규칙("자리가 사라지면 할 일이 없는 건지 기능이 없는 건지 구분되지 않는다")을 `StatTile`에도 적용합니다. `Tone=Attention`은 값이 1 이상일 때만 씁니다.
- **우측 열의 `확인 대기 건`은 모바일에 없던 블록입니다.** 대시보드가 "오늘 할 일"이라면 그 일의 실물이 여기 보여야 하고, 세로가 남는 데스크톱에서만 가능합니다. 3건까지 + `전체 보기` → A-6.
- **빈 상태**(등록 경기 0): `StatTile` 행을 그대로 두고(0 표시), 하단 2열 자리에 `경기 등록하기` CTA를 폭 전체로. 명세 §A-2의 "첫 사용 시 이 화면에서 막히면 안 된다"를 지킵니다.

### A-3 경기 목록 — `lg` 테이블

`PageHeader`(제목 `경기` + 우측 `경기 등록` Primary) → `SegmentedTab` 3탭 → `TableHeader` + `TableRow` × N.

| 열 | 폭 | 내용 |
|---|---|---|
| 일시 | 260 | `8월 13일 (금) 19:00` + 아래 줄에 구장명 (`TableRow`의 2행 첫 칸) |
| 선공 | 100 | `5/11` — `Numeric/Price` 우측 정렬 |
| 후공 | 160 | `6/11` — 인스턴스에서 `Numeric/Price`로 오버라이드 |
| 입금 대기 | 100 | `3건` — 0이면 `–`(회색), 1 이상이면 `text/brand` |
| 상태 | 94 | `StatusText` (`모집중`) |
| — | 170 | `chevron-right` (`액션 표시=false`, `화살표 표시=true`) |

**구장을 별도 열로 두지 않았습니다.** 첫 칸이 2행이라 일시 아래에 들어가고, 그렇게 하면 뒤 열들이 A-6과 같은 폭을 쓸 수 있습니다. 두 화면이 열 폭을 공유해야 `TableHeader`/`TableRow` 인스턴스를 그대로 재사용할 수 있습니다.

- **정렬 규칙은 명세 그대로**입니다(모집중·예정 오름차순, 종료 내림차순). 데스크톱이라고 열 헤더 클릭 정렬을 붙이지 않았습니다 — API에 정렬 파라미터가 없습니다(§8-2).
- 행 전체가 A-5로 가는 링크입니다. `MatchRow`와 같은 계약입니다.

### A-4 경기 등록 — `lg` split-side (5:3)

**이 화면이 데스크톱에서 가장 크게 개선됩니다.** 모바일 1329px 세로가 한 화면에 들어갑니다.

```
┌──────┬──────────────────────────────┬──────────────────┐
│      │ 경기 등록      [직전 경기와 동일하게]              │
│ ▣    ├──────────────────────────────┼──────────────────┤
│ ▤    │ 일시        [2026-09-06] [19:00]│ 슬롯 구성        │
│ ▥    │ 소요 시간    [2시간 ▾]         │ 선공 11 · 후공 11 │
│      │ 구장명      [상암구장    ]     │ ┌────┬────┐     │
│      │             (최근) 상암 잠실 목동│ │선발 ✓│선발 ✓│     │
│      │ 권장 급수    [무관 ▾]          │ │구원 ✓│구원 ✓│     │
│      │ 덕아웃      [선공 3루/후공 1루] │ │포수 ✓│포수 ✓│     │

│      │             [            ]    │ └────┴────┘     │
│      │                              │ 참가비           │
│      │                              │ 투수 13,000      │
│      │                              │ 포수 무료        │
│      │                              │ 야수 17,000      │
│      │                              │ 지타 13,000      │
│      ├──────────────────────────────┴──────────────────┤
│      │                        [ 취소 ]   [ 등록하기 ]    │
└──────┴─────────────────────────────────────────────────┘
```

- **슬롯 토글 22개를 선공/후공 2열로** 세웁니다. 같은 순번이 가로로 나란히 서므로 "포수를 양 팀 다 뺐나"가 눈으로 확인됩니다 — 모바일에선 22행을 스크롤해야 알 수 있었습니다.
- **일시가 여전히 첫 필드입니다.** 명세 §A-4의 근거("며칠에 할 건지가 이 화면의 첫 질문")는 폭과 무관합니다.
- **`직전 경기와 동일하게`는 `PageHeader`의 우측 액션**으로 올라갑니다. 폼 상단에 두면 첫 필드(일시)보다 위에 버튼이 오는데, 그건 이 화면의 첫 질문이 아닙니다.
- **하단 액션 바는 sticky**입니다. 우측 열이 길어 스크롤이 생기면 제출 버튼이 화면 밖으로 나갑니다.
- **수정 모드 제약**(신청자 있는 슬롯 토글 비활성, 참가비 잠금)은 그대로. 비활성 토글에 붙는 "신청자가 있어 뺄 수 없어요"는 데스크톱에서 행 옆 인라인 텍스트로 나갑니다.

### A-5 경기 상세 — `lg` split-side (5:3)

- **좌: 경기 요약 + 포지션 보드.** 선공·후공을 `SegmentedTab` 대신 **`split-even` 2열로 나란히** 놓습니다. 어드민이 "어디가 비었나"를 판단하는 화면인데, 탭이면 한 팀을 볼 때 다른 팀이 안 보여 판단이 두 번으로 쪼개집니다.
- **우: 예약 목록.** 탭 3개(입금 대기/확정/취소·거절) + 예약 카드. 카드는 모바일 것 그대로 — 슬롯 목록을 펼친 형태라 폭이 넓다고 구조가 바뀔 이유가 없습니다.
- **보드와 예약이 한 화면에 있는 것이 이 레이아웃의 요점입니다.** 좌측 보드에서 `홍길동`을 찾고 우측에서 그 예약의 입금 상태를 보는 동작이 스크롤 없이 됩니다.
- `PositionSlot Empty`의 어드민 오버라이드(값 `비어 있음`, `text/tertiary`, chevron 숨김)는 `lg`에서도 동일합니다.
- 하단 `출석 체크` 버튼은 좌측 열 아래 (경기 시작 시각 이후에만).

### A-6 입금 확인 — `lg` 테이블 ★

**모바일의 논리를 열로 옮깁니다. 정보의 우선순위는 바꾸지 않습니다.**

`PageHeader`(제목 `입금 확인`) → 필터 바(경기 `FilterChip` + 입금자명 검색 `TextField`) → `SegmentedTab` 2탭 → 테이블.

| 열 | 폭 | 내용 |
|---|---|---|
| 입금자명 | 260 | **`Heading/Small`.** 이 열이 제목입니다. 아래 줄에 슬롯 요약 (`선공 3루 홍길동 · 외 2자리`) |
| 금액 | 100 | `Numeric/Price` 우측 정렬. 0원은 `무료` |
| 경기 | 160 | `8/13(금) 19:00` |
| 신청 시각 | 100 | `8/4 21:10` |
| 상태 | 94 | `StatusBadge` |
| 액션 | 170 | `[거절] [입금 완료]` |

**슬롯을 독립 열로 두지 않았습니다.** 초안에서는 flex 열로 잡았는데, 나머지 열을 다 놓고 나면 남는 폭이 118px이라 두 버튼이 들어갈 자리가 사라집니다. 슬롯 요약을 입금자명 아래 줄로 내리면 액션에 170px이 확보되고, 모바일 카드의 정보 계층(입금자명이 제목, 슬롯은 그 아래)도 그대로 보존됩니다.

- **입금자명과 금액이 첫 두 열입니다.** 명세 §A-6의 근거("은행 앱에서 보는 값이 정확히 이 둘")를 열 순서로 옮긴 것입니다. 모바일에서 한 줄 양 끝이었던 것이 데스크톱에선 나란한 두 열이 됩니다 — 여러 행을 세로로 훑을 때는 오히려 이쪽이 대조가 빠릅니다. 금액은 우측 정렬 + tabular라 자릿수가 맞습니다.
- **섹션 구분은 그룹 헤더 행으로 유지합니다.** `입금 불필요` → `입금했다고 알려온 건` → `아직 입금 전` 순서. `SectionBand`를 테이블 폭으로 늘려 씁니다. 정렬(신청 시각 오름차순)도 섹션 내에서 그대로입니다.
- **액션 버튼이 행마다 노출됩니다.** 모바일과 달리 hover로 숨기지 않습니다. 어드민이 훑으며 연달아 누르는 동작인데 hover 노출이면 버튼 위치를 매번 눈으로 찾아야 합니다.
- **확인 다이얼로그는 그대로 유지합니다.** 데스크톱은 오조작이 쉽다고 흔히 말하지만 실제로는 반대입니다 — 돈 처리이고, 명세가 입금자명·금액 재확인을 요구합니다.
- **검색·필터가 항상 보입니다.** 모바일에선 스크롤하면 사라졌습니다. 대조 작업의 반은 "이름으로 찾기"라 이게 상주하는 것 자체가 데스크톱의 주된 이득입니다.
- **빈 상태:** `EmptyState` "확인할 입금이 없어요" — 테이블 헤더는 남기고 본문 자리에.

### A-7 출석 체크 — `lg` split-even

- 선공 11행 / 후공 11행을 2열로. **22행이 스크롤 없이 한 화면**에 들어갑니다.
- 슬롯 순서 유지(명세 §A-7 — "어드민이 보는 것은 라인업"). 2열이 되어도 좌=선공 1~11, 우=후공 1~11로 각 열 안에서 순번이 이어집니다.
- `대리` 배지 동일.
- **하단 sticky 제출 바**에 `22명 중 18명 체크` 진행 표시. 모바일은 세로 스크롤 중 몇 명 남았는지 알 수 없었는데, 전원 체크가 제출 조건이므로 이 수치가 필요합니다.
- 제출 확인 다이얼로그의 노쇼 경고 그대로.

### A-8 리그 설정 — `lg` 720 좌측 정렬

**폼은 넓히지 않습니다.** 라벨과 입력 사이가 멀어지면 시선이 가로로 길게 움직여 오히려 나빠집니다. 콘솔 본문 안에서 **720px 단일 열**로 좌측 정렬하고 나머지는 비웁니다.

- 섹션 4개(리그 정보 / 입금 계좌 / 티어별 참가비 / 계정)를 `SectionBand`로 구분.
- **좌측 앵커 내비를 두지 않았습니다.** 섹션이 4개뿐이라 스크롤 한 번이면 끝납니다.
- 입금 계좌 미입력 시 A-4에서 여기로 보내는 흐름(명세 §A-8)은 그대로. 도착 시 해당 섹션에 `border/danger` 강조.

## 7. 용병 화면 (P-1~P-11) — 2026-09-03 완료

Figma 페이지 `📱 Screens v2 @768` · `📱 Screens v2 @1280` (각 11화면) + 컴포넌트 `TopNav`. 전략은 착수 전에 적어 둔 대로 **중앙 정렬 컨테이너**입니다. 어드민과 달리 열을 쪼개지 않습니다 — 용병 화면은 탐색 → 신청 → 확인의 단일 흐름이고 비교·정렬 작업이 없어서 표 형태가 이득이 없습니다.

### 7.1 구간별 구조

| 구간 | 내비게이션 | 본문 | 프레임 |
|---|---|---|---|
| base | `BottomNav` 하단 고정 | full | 360×780 (기존 `📱 Screens v2`) |
| `md` | **`BottomNav` 그대로** — 768 폭으로 늘려 탭 4개 = 192px씩 | **640 중앙**, 상하 `spacing/2xl` 24 | 768×900. 콘텐츠가 길면 그만큼 (P-4 1270 · P-5 1655) |
| `lg` | **`TopNav` 64** 상단 | **640 중앙**, 상하 `spacing/3xl` 32 | 1280×800. 동상 (P-5 1121) |

- **`md`에서 `BottomNav`를 유지한 이유.** 768은 터치 태블릿이고, 세로로 잡은 아이패드에서 하단 탭은 표준 관용구입니다. 어드민이 `md`에서 레일 사이드바로 간 것은 3탭이 업무 도구였기 때문이고, 용병 4탭은 소비자 앱의 관용구를 따르는 편이 맞습니다. 탭 폭 192는 터치 타깃으로 충분합니다.
- **`lg`의 `TopNav`.** 1280 화면 하단에 고정된 4탭 바는 존재하지 않는 물건입니다(§3과 같은 논지). `TopNav` 좌측 워드마크가 로고 역할을 하므로 **P-3의 모바일 헤더(워드마크만 있던 것)는 `lg`에서 제거**했습니다. 나머지 화면의 헤더(뒤로가기 + 제목)는 그대로 640 열 안에 있습니다.
- 본문 640은 base 360의 1.78배지만, 화면의 최상위 섹션이 전부 `FILL`이라 폭만 바꾸면 내부가 따라옵니다. `MatchRow`·`ReservationRow`·`PositionSlot`은 좌우 끝에 정보가 붙는 행이라 폭이 늘어도 구조가 유지됩니다.

### 7.2 예외 화면

**P-1 로그인 — `md`·`lg` 모두 딥 그린 전면 + 중앙 400 열.** A-1의 흰 카드를 쓰지 않았습니다. P-1은 디자인 시스템에서 유일하게 `bg/brand-strong`이 전면에 깔리는 화면이고(design-system.md §6 "진한 그라운드 그린은 P-1에만"), 흰 카드를 얹으면 히어로 텍스트(`text/on-brand-strong`)를 전부 다시 칠해야 합니다. 히어로(마크 · 워드마크 · `RosterStrip`)와 푸터(카카오 버튼 · 약관)를 400 열에 `spacing/5xl` 48 간격으로 세로 중앙 정렬했습니다.

**P-4 경기 상세 · P-5 예약 신청 — `lg`에서 split (360 : FILL).** 착수 전 초안은 5:3(좌 정보, 우 보드)이었는데 **뒤집었습니다.**

```
┌ TopNav ───────────────────────────────────────────────────┐
│  ‹                                                        │
│  ┌ Info 360 ─┐  ┌ Board 584 ─────────────────────────┐    │
│  │ 일시 · 구장 │  │ 포지션 보드                          │    │
│  │ 참가비      │  │ 선공 (3루 덕아웃) · 5/11 │ 후공 (1루 덕아웃) · 6/11 │
│  │ 경기 정보   │  │  1 선발     김도현     │  1 선발     최민식  │    │
│  │ [신청하기]  │  │  2 구원  신청 가능 ›   │  2 구원     송강호  │    │
│  └───────────┘  │  … 11행               │  … 11행            │    │
│                 └────────────────────────────────────┘    │
└───────────────────────────────────────────────────────────┘
        컨테이너 976 = 360 + 32 + 584 — A-5 `lg`와 같은 수치, 좌우만 바뀜
```

- **정보 열이 360인 이유.** 모바일 폭 그대로라 Summary · Fee · MatchPoint · Footer 블록을 수정 없이 옮길 수 있고, 내용이 텍스트 몇 줄이라 넓혀 봐야 빈 면만 늘어납니다.
- **보드 열이 넓은 이유.** 보드가 이 화면의 시그니처이고, 22행이 한 화면에 들어가려면 두 팀을 나란히 놓아야 합니다. 584를 `spacing/3xl` 32로 나눠 팀당 276 — A-5 `lg`의 보드 열과 정확히 같은 폭이라 `PositionSlot`이 이미 검증된 폭입니다. `SegmentedTab`은 `lg`에서 사라지고 **팀 라벨**(`Label/Medium` + `text/secondary`, `선공 (3루 덕아웃) · 5/11`)이 그 자리를 대신합니다. 보드 헤더의 충원 수(`5/11`)도 팀 라벨로 내려갔습니다.
- **P-5는 선택 상태가 두 팀에 걸쳐 보입니다.** 명세 §P-5 "선공·후공을 섞어서 고를 수 있습니다"가 모바일에선 탭을 오가야 확인됐는데 `lg`에선 한 화면입니다. 좌측 폼 열(선택 요약 → 참가자 이름 → 입금자명 → 제출)은 모바일 순서 그대로입니다.
- **하단 CTA는 정보 열 맨 아래.** 모바일 Footer(상단 헤어라인 + 버튼)를 그대로 옮겼습니다. 정보 열이 보드 열보다 짧아 버튼이 항상 화면 안에 있으므로 sticky가 필요 없습니다.
- **`md`에서는 두 화면 모두 단일 열(탭 유지)** 입니다. 640에서 두 팀을 나란히 놓으면 팀당 304로 가능은 하지만, 태블릿에서까지 레이아웃을 갈라 목업을 셋으로 늘릴 이유가 없었습니다.

**P-2 프로필 설정 — `lg`에 `TopNav` 없음.** 온보딩은 탭 진입 전이라 내비를 그릴 근거가 없습니다(A-1과 같은 이유). 640 열만 중앙에 둡니다.

### 7.3 `TopNav` (컴포넌트 #30)

`Active` 4변형 (Games / Reservations / Notifications / MyPage) + `배지 표시` BOOLEAN + `배지 값` TEXT.

- **1280×64.** `height`를 `size/topnav-height`에 바인딩. 좌우 패딩 `spacing/3xl`, 하단 `border/subtle` 1px (`border-width/thin`).
- **좌측 워드마크 90×24** — P-3 모바일 헤더와 같은 크기. 우측 탭 4개.
- **탭 = 아이콘 24 + `Label/Medium`, 높이 44** (터치 타깃 규칙 §4 유지), `radius/md`. 활성 `bg/brand-subtle` + `text/brand` · `icon/brand`, 비활성 `text/secondary` · `icon/secondary`. `SideNav Full` 항목과 같은 문법입니다.
- **알림함 배지**는 `SideNav`의 pill(`bg/brand` + `text/on-brand`, `Label/Small`, `radius/full`)을 그대로 씁니다. 대비는 §4 실측(4.66 / 5.25) 조합과 동일합니다.
- 아이콘은 `BottomNav`와 동일: calendar · check · bell · user.
- 탭 라벨은 `BottomNav`의 `마이`가 아니라 **`마이페이지`** 전체입니다. 하단 탭에서 줄인 것은 폭 때문이었고, 상단 내비에는 그 제약이 없습니다.
- 인스턴스는 폭 `FILL`로 화면에 붙입니다. 1440 초과 화면에서의 잠금은 코드 단계에서 — 내비 안쪽에 `size/container-console` max-width 컨테이너를 두면 됩니다.

## 10. 작업 중 드러난 것 (재작업 시 주의)

`design-system.md` §9의 함정 목록에 이어지는 항목들입니다.

20. **아이콘은 fill이 아니라 stroke로 칠합니다.** `Icon/*` 컴포넌트의 벡터는 `fills: []`이고 `strokes`가 변수에 바인딩돼 있습니다. 인스턴스를 재색상할 때 `v.fills = [paint]`를 쓰면 열린 패스가 채워져 **캘린더 아이콘이 검은 사각형이 됩니다.** `v.fills = []; v.strokes = [paint]`가 맞습니다. 스크린샷 없이는 데이터만 보고 못 잡습니다.

21. **컴포넌트 내부 노드 이름을 추측하지 마세요.** `PositionSlot`의 프로퍼티 이름은 `값`인데 **노드 이름은 `Value`** 입니다. `findOne(n => n.name === '값')`이 조용히 `null`을 반환해 A-5의 어드민 오버라이드가 통째로 누락됐고, 감사 스크립트는 인스턴스 내부를 건너뛰기 때문에 잡히지 않았습니다. 오버라이드 전에 `findAll`로 실제 이름을 먼저 확인하세요.

22. **`PositionSlot` Empty에는 chevron이 없습니다.** `design-system.md` §6.1이 "내부 chevron 노드를 `visible = false`"라고 적어 뒀지만, 현재 Empty 변형의 자식은 `Num`·`Position`·`Value` 텍스트 3개뿐입니다. 어드민 오버라이드에서 실제로 필요한 건 **`Value`의 fill을 `text/brand` → `text/tertiary`로 바꾸는 것 하나**입니다. §6.1 문장을 고쳐야 합니다.

23. **프로퍼티 키는 `이름#id` 형태라 하드코딩하지 마세요.** `set.componentPropertyDefinitions`의 키에서 `k.split('#')[0]`으로 이름을 매칭하는 헬퍼를 쓰면 컴포넌트를 다시 만들어도 스크립트가 깨지지 않습니다.

24. **`FILL` 높이 노드로 프레임 높이를 재면 항상 프레임 높이가 나옵니다.** A-8의 콘텐츠가 넘치는지 보려고 `Main.height`를 쟀는데 `Main`이 `layoutSizingVertical = FILL`이라 언제나 프레임과 같았습니다. 안쪽의 HUG 노드(`Form`)를 재야 합니다.

25. **다른 페이지의 노드는 페이지 전환 없이 복제해 옮길 수 있습니다.** `await figma.getNodeByIdAsync(id)`로 잡은 뒤 `clone()` → 현재 페이지의 프레임에 `appendChild`. 용병 22화면을 이 방법으로 만들었고, 스크립트마다 `setCurrentPageAsync`는 대상 페이지로 한 번뿐입니다. 복제 뒤 반드시 할 일 세 가지: ① `BottomNav`를 밖으로 빼고 ② `layoutSizingVertical = FILL`인 자식(`List` · `Spacer`)을 `HUG`로 바꾸거나 지우고 ③ `resize(640, h)` 뒤 `primaryAxisSizingMode = 'AUTO'`를 다시 지정. ②를 빼먹으면 함정 15(HUG 부모 안의 FILL 자식)가 그대로 재현됩니다.

26. **`setBoundVariable('height', var)`는 프레임·컴포넌트에서 됩니다.** `TopNav` 4변형의 높이를 `size/topnav-height`에 바인딩했습니다. `SideNav`는 높이가 인스턴스마다 다르므로 바인딩하지 않은 것이 맞고, 높이가 고정인 내비만 바인딩합니다.

27. **인스턴스 축소는 `rescale()`.** 워드마크 210×56을 헤더용 90×24로 줄일 때 `resize()`를 쓰면 내부 벡터가 안 따라옵니다. `inst.rescale(24 / 56)`이 자식까지 비례 축소합니다. P-3 모바일 헤더의 90×24와 같은 크기가 나옵니다.

28. **인스턴스의 TEXT 프로퍼티를 `setProperties`로 바꾸려면 폰트를 먼저 로드해야 합니다.** `PositionSlot`의 `값`에 이름을 넣을 때 Noto Sans KR 3종 + Roboto Mono를 로드하지 않으면 실패합니다. 키는 함정 23대로 `k.split('#')[0] === '값'`으로 찾습니다.
