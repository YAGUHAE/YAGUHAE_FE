## 0. 이 페이지는 무엇인가

**리그 하나를 운영하는 사람이 쓰는 관리 페이지**입니다. 계정은 **리그당 1개**이고, 그 계정이 보고 만질 수 있는 것은 **자기 리그에 속한 데이터뿐**입니다.

하는 일은 셋입니다.

| 하는 일 | 화면 |
| --- | --- |
| **용병 경기 일정을 올린다** — 며칠에 경기를 하는지, 어느 구장인지, 자리를 몇 개 여는지 | A-4 |
| **입금 내역을 확인하고 입금 완료로 바꾼다** — 은행 앱의 입금 내역과 신청 건을 대조해 확정 처리 | A-6 (·A-5) |
| **자기 리그 경기와 신청 현황을 본다** — 누가 어느 자리에 들어왔는지, 몇 자리가 남았는지 | A-3, A-5 |

부수적으로 경기 당일 **출석·노쇼 처리**(A-7)와 **리그 기본 정보·참가비 설정**(A-8)이 붙습니다. 노쇼 처리는 용병 문서의 `NO_SHOW` 상태를 만드는 유일한 경로이므로 누군가는 해야 하고, 현장에 있는 사람은 리그 어드민뿐입니다.

**하는 일이 아닌 것** — 유저 정지 해제, 문의 처리, 다른 리그 조회. 이유는 §6.

### 계정 모델

- `league_admin` 계정과 `league`는 **1:1**입니다. 로그인하면 곧바로 자기 리그 컨텍스트로 들어갑니다. 리그 선택 화면이 없습니다.
- **계정은 사람이 아니라 리그에 귀속됩니다.** 운영자가 바뀌면 계정을 넘겨받습니다.
- 그래서 **용병용 카카오 로그인과 분리된 ID/PW 로그인**을 씁니다(A-1). 개인 소셜 계정에 묶어두면 운영자 교체 때 계정째 잃습니다.
- 계정 발급은 서비스 운영자가 합니다(§6).

### 왜 데스크톱이 아니라 모바일인가

입금 확인이 이 페이지의 중심 업무인데, 그 작업은 **은행 앱과 번갈아 보는 일**입니다. 두 앱 모두 폰에 있습니다. 경기 당일 출석 체크도 구장에서 폰으로 합니다. 데스크톱 콘솔은 만들지 않습니다.

### 하단 탭

`경기(A-3) · 입금 확인(A-6) · 리그(A-8)` 3탭.

입금 확인을 탭으로 올린 이유: 경기 안에 묻어두면 "오늘 확인할 입금이 있는지"를 알려면 경기를 하나씩 열어봐야 합니다. 미처리 건수 배지를 탭에 달아 앱을 열자마자 보이게 합니다.

## 2. 화면별 상세 명세

### A-1. 어드민 로그인

- **구성:** 아이디, 비밀번호, `로그인` 버튼. 소셜 로그인 없음
- **성공:** A-2로 이동. 세션에 `leagueId`가 실립니다 — 이후 모든 화면이 이 리그로 고정됩니다
- **실패:** "아이디 또는 비밀번호를 확인해주세요" 인라인 에러. 어느 쪽이 틀렸는지 구분해 알려주지 않습니다
- **비밀번호 재설정:** v1은 서비스 운영자 문의 안내 문구만 둡니다(자동 재설정 메일 경로 없음 — 계정에 개인 이메일이 붙지 않으므로)
- **연동 API:** `POST /admin/auth/login`

### A-2. 홈 (대시보드)

- **헤더:** 리그명 + 오늘 날짜
- **처리 대기 카드 2개**
  - `입금 확인 대기 N건` → A-6
  - `오늘/내일 경기 N개` → A-3
- **카드는 0건이어도 숨기지 않고 `0`으로 표시합니다.** 자리가 사라지면 "할 일이 없는 상태"인지 "기능이 없는 것"인지 구분되지 않습니다
- **하단:** 다가오는 경기 3건 요약(일시·구장·충원 `선공 4/11 · 후공 6/11`) → 탭하면 A-5
- **빈 상태:** 등록된 경기가 하나도 없으면 `경기 등록하기` CTA를 카드 대신 크게 노출합니다. 첫 사용 시 이 화면에서 막히면 안 됩니다
- **연동 API:** `GET /admin/dashboard`

### A-3. 경기 목록

- **탭:** 모집중 / 예정(마감) / 종료
- **리스트 아이템:** `GameCard` 재사용 + 관리용 정보 추가
  - 일시, 구장명, 충원 현황(`선공 4/11 · 후공 6/11`)
  - **입금 확인 대기 배지** (N건 있을 때만, 강조색)
- **정렬:** 모집중·예정은 경기일 오름차순(가까운 것부터), 종료는 내림차순(최근 것부터)
- **상단 액션:** `경기 등록` 버튼 → A-4
- **아이템 클릭:** A-5
- **빈 상태:** 탭별 문구 + `경기 등록` 버튼
- **연동 API:** `GET /admin/games?status=`

### A-4. 경기 등록 / 수정

**"용병 경기를 며칠에 할 건지 올리는" 화면입니다.** 리그 어드민이 가장 자주 여는 생성 화면이므로 입력 개수를 최소로 잡습니다.

- **입력 필드**
  - **일시** (필수) — 날짜 + 시작 시각
  - **소요 시간** (필수, 기본 2시간)
  - **구장명** (필수) — 최근 사용한 구장 3개를 칩으로 제안
  - 권장 급수 (선택 — **제한이 아니라 표시용**, 용병 §3.3)
  - 덕아웃 표기 (선택, 예: `선공 3루 / 후공 1루`)
  - 안내 문구 (선택, 자유 텍스트 — 주차·집합 시간 등)
- **슬롯 구성**
  - 기본 프리셋 11개(선발·구원·포수·1~3루·유격·좌중우익·지타)가 **선공·후공 각각** 들어가 있습니다
  - 슬롯별 **사용 여부 토글**로 빼거나 넣습니다. 순서 변경은 v1에서 제공하지 않습니다
  - 현재 인원 표기: `선공 11자리 · 후공 11자리`
- **참가비:** 리그 기본값(A-8)이 프리필됩니다. 이 경기만 다르게 받을 일이 있으면 덮어쓸 수 있습니다. 티어 4종(투수·포수·야수·지타)
- **`직전 경기와 동일하게` 버튼** — 최근 등록한 경기의 구장·슬롯 구성·참가비·안내 문구를 그대로 복사하고 **일시만 비웁니다.** 리그는 보통 같은 구장에서 정기적으로 돌기 때문에, 매번 11×2 슬롯을 다시 확인하게 만들면 등록 자체가 부담이 됩니다
- **제출:** `POST /admin/games` — 성공 시 A-5로 이동
- **수정 시 제약**
  - 이미 신청자가 있는 슬롯은 **끌 수 없습니다.** 토글이 비활성화되고 "신청자가 있어 뺄 수 없어요" 안내
  - 참가비는 **신청자가 1명이라도 있으면 수정 불가**입니다. 이미 안내된 금액으로 입금이 진행 중이므로 바꾸면 대조가 깨집니다
  - 일시·구장 변경 시 확인 다이얼로그 + 신청자 전원에게 알림 발송

### A-5. 경기 상세 (신청 현황)

- **상단:** 경기 요약(일시·구장) + 충원 현황(`선공 4/11 · 후공 6/11`)
- **포지션 보드:** 용병 P-4와 **같은 보드를 그대로 재사용**합니다. 슬롯별 참가자 이름, 빈자리 표시
  - 어드민이 확인하고 싶은 것도 용병과 같은 질문("어디가 비었나")이고, 실제로 새 공고를 올릴지 판단하는 근거가 이 보드입니다
  - 빈 슬롯은 어드민 화면에서는 탭 불가(신청은 용병만)
- **탭:** 입금 대기 / 확정 / 취소·거절
- **리스트 아이템 = 예약 1건** (슬롯 N개, 용병 §3.2)
  - 신청자 닉네임, **입금자명**, 신청 시각, 상태 배지
  - **슬롯 목록을 아이템 안에 펼칩니다** — `선공 3루 · 홍길동`, `선공 유격 · 김철수` …
  - **합계 금액** (강조)
- **액션:** 입금 대기 탭의 아이템에서 바로 `입금 완료` / `거절` — 동작은 A-6과 동일합니다
- **하단 버튼:** 경기 시작 시각 이후 `출석 체크` 노출 → A-7. 확정(`APPROVED`) 참가자가 한 명도 없으면 비활성 + "확정된 참가자가 없어요"
- **연동 API:** `GET /admin/games/:id`, `GET /admin/games/:id/reservations?status=`

### A-6. 입금 확인 ★

이 페이지의 핵심 화면입니다. **은행 앱의 입금 내역과 신청 건을 눈으로 대조하는 작업**을 최대한 짧게 만드는 것이 목표입니다.

#### 상태 흐름에서의 위치

용병 문서의 상태머신을 그대로 씁니다. 새 상태를 만들지 않습니다.

| 시점 | 상태 | 누가 |
| --- | --- | --- |
| 신청 | `RESERVED` | 용병 (P-5) |
| "입금했어요" 셀프 체크 | `PAYMENT_SUBMITTED` | 용병 (P-6) |
| **실제 입금 대조 후 확정** | `APPROVED` | **리그 어드민 (여기)** |
| 입금 없음·중복 등으로 반려 | `REJECTED` | 리그 어드민 |

> **"승인"이라는 별도 판단은 없습니다.** 어드민이 하는 일은 돈이 들어왔는지 확인하는 것 하나이고, 확인되면 곧 확정입니다. 그래서 버튼 문구도 `승인`이 아니라 **`입금 완료`**입니다. 사람을 심사하는 화면이 아니라 장부를 맞추는 화면이라는 게 문구에서 드러나야 합니다.

#### 구성

- **탭:** 확인 대기 / 확인 완료
- **확인 대기 = `PAYMENT_SUBMITTED` + `RESERVED`를 함께 보여줍니다**
  - `PAYMENT_SUBMITTED`(용병이 입금했다고 체크함)가 위, `RESERVED`(아직 체크 안 함)가 아래
  - 섹션 헤더로 구분: `입금했다고 알려온 건` / `아직 입금 전`
  - 왜 `RESERVED`도 보여주는가: 체크를 잊고 입금만 한 사람이 실제로 있습니다. 은행 내역에 이름이 있는데 목록에 없으면 어드민이 찾을 데가 없습니다
- **리스트 아이템 — 대조에 필요한 것만**

  ```
  ┌──────────────────────────────────┐
  │ 김철수            34,000원  [배지] │   ← 입금자명 · 금액을 같은 줄 양끝에
  │ 8/9(토) 19:00 · 상암구장           │
  │ 선공 3루 홍길동 · 선공 유격 김철수   │
  │ 신청 8/4 21:10                    │
  │        [ 거절 ]     [ 입금 완료 ]  │
  └──────────────────────────────────┘
  ```
  - **입금자명과 금액을 한 줄 양 끝에 크게** 둡니다. 은행 앱에서 보는 값이 정확히 이 둘이고, 나머지는 그 다음입니다
  - 닉네임이 아니라 **입금자명이 제목**입니다. 은행 내역에는 닉네임이 없습니다
  - 슬롯 목록은 한 줄 요약(넘치면 `외 N자리`), 탭하면 펼침
- **정렬:** 신청 시각 오름차순(오래된 것부터). 만료(24h)가 가까운 건이 위로 올라옵니다
- **필터:** 경기별 필터 칩. 기본은 **전체 경기 합산**입니다 — 은행 내역은 경기 단위로 오지 않으므로, 이름 하나를 찾을 때 경기를 옮겨 다니게 하면 안 됩니다
- **검색:** 입금자명 검색 필드. 대조가 안 맞는 건 결국 이름으로 찾습니다
- **액션**
  - `입금 완료` → 확인 다이얼로그(입금자명·금액 재확인) → `PATCH /admin/reservations/:id/confirm-payment` → `APPROVED`
  - `거절` → 사유 선택(미입금 / 금액 불일치 / 중복 신청 / 기타) → `PATCH /admin/reservations/:id/reject` → `REJECTED`, 슬롯이 다시 열립니다
  - 둘 다 처리 후 알림이 신청자에게 발송됩니다(용병 P-11)
- **금액 불일치 안내:** 합계와 다른 금액이 들어온 경우를 앱이 알 수 없습니다(은행 연동 없음). 어드민이 눈으로 보고 `거절 → 사유: 금액 불일치`를 고르면 신청자에게 사유가 그대로 전달됩니다
- **0원 예약:** 합계가 0원인 예약(포수 무료 등)은 `입금 불필요` 배지와 함께 별도 섹션 최상단에 둡니다. 확인할 입금 내역이 없으므로 `입금 완료`만 누르면 됩니다
  - 신청 즉시 자동 확정할지는 서버와 맞춰야 합니다(용병 §2-2). 현재 문서는 **어드민이 한 번 누르는 전제**입니다 — 노쇼 방지용 최소 확인 절차로 남깁니다
- **빈 상태:** "확인할 입금이 없어요"
- **연동 API:** `GET /admin/payments?status=&gameId=&q=`

### A-7. 출석 체크

- **진입:** A-3 또는 A-5에서 경기 시작 시각 이후 노출되는 `출석 체크` 버튼
- **팀 탭:** 상단에 `선공` / `후공` 2탭(`SegmentedTab`). 진입 시 **선공**이 선택돼 있습니다
  - 한 번에 **한 팀의 라인업만** 보여줍니다. 어드민은 선공 덕아웃 앞에 서서 그 팀만 부르는데, 두 팀 22명을 한 리스트에 이어 붙이면 현장에서 쓰는 단위와 화면이 어긋납니다
  - A-5(= 용병 P-4)의 포지션 보드가 이미 같은 팀 탭을 씁니다. 어드민은 방금 본 구조 그대로 출석 화면에 들어옵니다
  - 탭 라벨은 A-5와 같은 `선공 (3루 덕아웃)` / `후공 (1루 덕아웃)`입니다
- **진행률 한 줄:** 탭 바로 아래에 **두 팀 진행률을 함께** 둡니다 — `선공 체크 11/11 · 후공 체크 5/11`. 체크할 때마다 실시간으로 갱신됩니다
  - 진행률을 탭 라벨 안에 넣지 않은 이유: 한 줄로 빼면 **어느 탭을 보고 있든 두 팀 숫자가 동시에** 보입니다. 탭 라벨에 넣으면 각 팀의 숫자가 그 탭에 종속돼, 정작 막아야 할 "반대 팀이 안 보인다"를 절반만 해결합니다
- **`체크 11/11`의 분모는 슬롯 수가 아니라 그 팀의 `APPROVED` 인원입니다.** 미충원 슬롯·거절·취소된 자리는 출석 대상이 아니므로 행 자체가 없습니다
  - 그래서 다른 화면의 충원 표기(`선공 4/11`)와 **같은 형태로 쓰지 않습니다.** 분모가 우연히 같은 숫자일 뿐 다른 값이고, 포맷까지 같으면 섞여 읽힙니다. `체크`라는 낱말이 그 구분을 집니다 — A-4의 `선공 11자리 · 후공 11자리`가 이미 쓰는 방식입니다
- **구성:** 선택된 팀의 `APPROVED` 참가자를 **슬롯 순서대로** 나열. 각 행에 참가 / 노쇼 2지선다 토글
  - 슬롯 순서로 나열하는 이유: 어드민이 실제로 보는 것이 라인업입니다. 닉네임 가나다순은 현장에서 쓸모없습니다
  - 팀 간 정렬은 탭이 대신합니다. 한 탭 안에서는 선발·구원·포수·1~3루·유격·좌중우익·지타 순서 그대로입니다
- **대리 신청분 처리:** 동행자 슬롯의 노쇼는 **신청자 계정에 누적**됩니다(용병 §3.2). 행에 `대리` 표시를 붙여 어드민이 인지하게 합니다
- **탭을 바꿔도 체크 상태는 유지됩니다.** 탭은 필터일 뿐입니다 — 용병 P-5가 슬롯 다중 선택에 이미 같은 규칙을 씁니다(용병 §P-5)

#### 미체크가 반대 탭에 숨지 않게 하는 장치 3종

화면을 반으로 접었으니 **한쪽만 보고 제출하는 경로**가 생겼습니다. 제출은 되돌릴 수 없으므로(§6-4) 세 곳에서 막습니다.

| 장치 | 내용 |
| --- | --- |
| **① 탭 아래 두 팀 진행률** | 어느 탭을 보고 있든 반대 팀이 몇 명 남았는지 항상 보입니다 |
| **② 제출 바의 미체크 안내** | 제출 버튼 위 한 줄. **탭하면 미체크가 남은 탭으로 이동**합니다 |
| **③ 제출 다이얼로그의 팀별 요약** | 탭이 정보를 갈라놓았으므로, 다이얼로그가 **두 팀을 한 화면에서 보는 유일한 지점**이 됩니다 |

②의 문구는 미체크 인원이 어디 있느냐에 따라 갈립니다.

| 미체크 위치 | 문구 | 제출 버튼 |
| --- | --- | --- |
| 반대 탭에만 | `후공 6명이 아직 미체크예요 ›` | 비활성 |
| 현재 탭에만 | `아직 3명 남았어요` | 비활성 |
| 양쪽 다 | `선공 2명 · 후공 6명 미체크 ›` (먼저 남은 팀으로 이동) | 비활성 |
| 없음 | 문구 없음 | **활성** |

②는 **버튼 라벨이 아니라 버튼 위의 별도 한 줄**입니다. 사유를 비활성 버튼 라벨에 넣으면(`2명 더 체크하면 제출할 수 있어요`) 짧아 보이지만, **비활성 버튼은 탭 타깃이 될 수 없어 이동 경로가 사라집니다.** 버튼 라벨은 `제출`로 두고, 안내는 브랜드색 텍스트 링크로 분리합니다.

- **제출:** `POST /admin/games/:id/attendance` — **두 팀을 한 번에 보내는 일괄 제출 1회**입니다. 양 팀 전원을 체크해야 버튼이 활성화됩니다
  - **탭은 필터이지 제출 단위가 아닙니다.** 팀별 분할 제출을 만들지 않는 이유: 되돌릴 수 없는 제출이 2개로 늘고, "선공만 제출된 경기"라는 중간 상태가 새로 생깁니다
  - 슬롯이 이미 팀을 들고 있으므로 **요청 바디는 팀 탭 도입 전과 동일**합니다. 이번 변경은 화면에서만 일어납니다
- **제출 후:** 되돌릴 수 없습니다. 제출 전 확인 다이얼로그에 팀별 노쇼 요약(`노쇼 3명 — 선공 1 · 후공 2`)과 "노쇼 처리된 인원은 신청이 제한될 수 있어요" 경고
  - 잘못 눌렀을 때의 정정 경로가 리그 어드민에게 없습니다 — §6-4
- **한 팀의 `APPROVED`가 0명:** 그 탭은 "출석 대상이 없어요" 빈 상태로 두고 제출 조건에서 제외합니다. 한쪽 팀만 채워진 채 경기일을 맞는 경우가 실제로 있습니다(용병 §P-4 — 한쪽 팀이 다 차도 나머지 팀은 계속 열려 있습니다)
- **양 팀 모두 0명:** A-5의 `출석 체크` 버튼을 비활성화하고 "확정된 참가자가 없어요"를 답니다. A-7에 진입시키지 않습니다

### A-8. 리그 설정

- **리그 정보:** 리그명, 활동 지역, 소개, 대표 구장(A-4 프리필용)
- **입금 계좌** (필수) — 은행 / 계좌번호 / 예금주
  - 용병 P-6 입금 안내에 그대로 노출되는 값입니다. **비어 있으면 경기를 등록할 수 없습니다** — A-4 제출 시 검증하고 이 화면으로 보냅니다
- **티어별 참가비 기본값 4종** (투수·포수·야수·지타)
  - 여기가 정본이고 경기 생성 시 복사됩니다(용병 §3.1). **이미 만들어진 경기의 금액은 바뀌지 않습니다** — 안내 문구로 명시
  - 0원 허용, `무료`로 표기
- **계정:** 비밀번호 변경, 로그아웃
- **연동 API:** `GET /admin/league`, `PATCH /admin/league`

## 6. 확인이 필요한 항목

1. **정지 해제·문의 처리를 누가 하는가 (가장 중요)**
   용병 §3.3은 "정지 해제는 어드민이 수동 처리"를 전제로 하고, P-4·P-5·P-10 세 화면에 `문의하기`가 있습니다. 그런데 `is_suspended`는 **리그와 무관한 계정 전역 값**입니다. A리그 어드민이 이걸 풀면 B리그에도 효력이 갑니다 — 리그당 1계정 모델과 충돌합니다.
   → **서비스 운영자(플랫폼 관리자) 역할을 따로 두는 것을 권합니다.** 문의함·유저 관리·리그 어드민 계정 발급이 그쪽으로 갑니다. 확정되면 `docs/screen-design-superadmin.md`로 분리해 작성합니다. 그전까지 용병의 `문의하기`는 닿을 곳이 없습니다.

2. **어드민 계정 발급 절차** — 위 1번과 함께 결정됩니다. 리그 생성과 계정 발급이 한 세트인지, 리그를 먼저 만들고 계정을 붙이는지.

3. **어드민의 포지션 조정** — 용병 P-8에 "주최자가 승인 시 다른 슬롯으로 옮긴 경우" 문구가 있지만 A-5·A-6에 조정 UI를 넣지 않았습니다. 입금 확인은 돈 확인이지 자리 재배치가 아니라는 게 이 문서의 입장입니다. **v1에서 제공하지 않는 쪽을 권하며, 그렇다면 P-8의 해당 문구를 지워야 합니다.**

4. **A-7 출석 제출 이후 정정** — 되돌릴 수 없게 뒀습니다. 잘못 누른 노쇼를 뺄 경로가 리그 어드민에게 없고, 1번의 서비스 운영자가 생겨야 해결됩니다. 어드민 스스로 경기 종료 후 N시간 내에는 정정 가능하게 할지 확정 필요.
   v2.1의 팀 탭이 여기에 얹히는 위험이 하나 있습니다 — **한 탭만 보고 성급히 제출하는 경로**입니다. A-7의 장치 3종으로 막았지만 그건 실수를 어렵게 만드는 것일 뿐, 일어난 실수를 되돌리지는 못합니다. 정정 경로가 없는 한 이 항목은 열려 있습니다.

5. **금액 불일치 처리** — 은행 연동이 없으므로 앱은 실제 입금액을 모릅니다. 현재는 `거절 → 사유: 금액 불일치`로만 처리합니다. 부분 입금(예: 3자리 중 2자리분만 입금) 상황을 별도로 다룰지 미정입니다.

6. **A-6 확인 대기에 `RESERVED`를 섞는 범위** — 만료 전 24시간 내 건만 보여줄지, 전부 보여줄지. 현재는 전부입니다.

7. **경기 일괄 등록** — 정기전이면 "매주 토요일 8주치"를 한 번에 올리고 싶어집니다. v1은 단건 등록 + `직전 경기와 동일하게`(A-4)로 처리하고, 반복 등록은 v2 후보로 둡니다.
