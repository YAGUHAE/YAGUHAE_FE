# 화면설계서 (용병 / Player) v1

> **문서 정보**
>
> - **최종 수정일:** 2026-07-14
> - **기반 문서:** ERD + 상태머신 (NestJS + TypeORM 재정비판 v3), API 명세 (NestJS)
> - **범위:** 용병(Player) 화면. 주최자(Host) 화면은 별도 문서에서 다룸
> - **작성 원칙:** 화면마다 "무엇을 보여주는지 + 어떤 API를 호출하는지 + 상태별로 뭐가 달라지는지 + 실패 시 뭘 보여주는지"를 함께 명시. 순수 레이아웃(피그마 목업)은 다음 단계에서 별도 진행

| --- | --- | --- | --- |

| P-3 | 경기 목록 (홈) | 신청 가능한 경기 탐색 | 로그인 완료 후 기본 화면, 하단 탭 |

| P-9 | 평가 작성 | 경기 종료 후 동참자 평가 + 베스트플레이어 투표 | P-7/P-8에서 ATTENDED 건, 또는 알림 클릭 |

**하단 탭 구성 (항상 노출):** 경기 목록(P-3) · 내 예약(P-7) · 알림함(P-11) · 마이페이지(P-10)

## 1. 화면별 상세 명세

### P-1. 카카오 로그인

- **구성 요소:** 서비스 로고/슬로건, "카카오로 시작하기" 버튼 1개
- **동작:** 버튼 클릭 → 카카오 OAuth 콜백 → 서버에서 `provider`/`provider_id` 매칭
  - 기존 유저 → P-3 (경기 목록)로 이동
  - 신규 유저 → P-2 (프로필 설정)로 이동
- **에러 상태:** OAuth 실패/취소 시 로그인 화면에 토스트("로그인에 실패했어요, 다시 시도해주세요")로 복귀

### P-2. 프로필 설정 (온보딩)

- **입력 필드**
  - 닉네임 (필수, 텍스트)
  - 활동 지역 (필수, 지역 선택)
  - 주 포지션 (선택, Position enum 단일 선택 — 프로필 표시용 + P-5에서 기본 선택값 제안에 사용. 이 포지션으로만 신청 가능하다는 제약은 아님, §3 참고)
  - 본인 주장 급수 self_level (필수, LevelEnum 단일 선택 — "정직하게 입력해주세요. 경기 참가를 막지는 않지만, 주최자가 팀을 짤 때 참고해요" 안내 문구)
    - **참가 제한 용도가 아닙니다**(§3.3). 주최자 참고 + P-9의 "실력-프로필 일치도" 평가 근거로만 씁니다
  - 게임원/유니크플레이 프로필 URL (선택, URL 입력 — 형식 검증만, 접근 가능 여부는 검증하지 않음)
- **제출:** "시작하기" 버튼 → 프로필 저장 API 호출 → P-3 이동
- **검증 실패:** 닉네임 중복/미입력, 필수 필드 미입력 시 인라인 에러 메시지. 화면 전환 없음

### P-3. 경기 목록 (홈)

- **상단:** 필터 바 — 지역, 날짜, 권장 급수 (다중 아님, 단일 선택 드롭다운/칩)
  - 급수 필터는 **탐색 보조일 뿐 신청을 막지 않습니다**(§3.3). 필터를 걸지 않으면 모든 급수의 경기가 나옵니다
- **리스트 카드 (경기별):** 경기장, 일시(날짜+시간), 참가비 최저가(`13,000원부터` — 티어 4종을 카드에 나열하지 않음, §3.1), 권장 급수, 팀별 충원 요약(예: "선공 4/11 · 후공 6/11"), 비어 있는 대표 포지션 칩(최대 2개, 예: `포수 모집` `3루 모집`), 경기 상태 배지(모집중/마감/취소)
  - 대표 포지션 선정 기준: 빈 슬롯 중 슬롯 순번이 빠른 순. 빈 슬롯이 3개를 넘으면 마지막 칩은 `+N`으로 축약
  - 목록 카드에는 참가자 이름을 표시하지 않습니다(포지션 보드는 P-4에서만)
- **빈 상태:** 필터 조건에 맞는 경기가 없을 때 "조건에 맞는 경기가 없어요" + 필터 초기화 버튼
- **연동 API:** `GET /games` (필터 쿼리 파라미터)
- **카드 클릭:** P-4로 이동
- **정지 유저 처리:** `is_suspended=true`인 경우 목록은 그대로 보이되, 카드 클릭 시 P-4에서 안내(§P-4 참고)

### P-4. 경기 상세

- **표시 정보:** 경기장명, 일시, 소요시간, **포지션별 참가비 요약**, 권장 급수, 리그명, **팀별 포지션 보드(선공·후공 각 1블록)**, 경기 상태
  - 참가비 요약: 티어 4종을 한 줄로 (예: `투수 13,000 · 포수 무료 · 야수 17,000 · 지타 13,000`). 금액이 0원인 티어는 `무료`로 표기하고 강조색을 씁니다
  - 티어 정의와 포지션 매핑은 §3.1 참고

#### 포지션 보드

경기 상세의 핵심 요소입니다. 어느 포지션이 찼고 어디가 비었는지를 한눈에 보여주고, 빈 자리를 그대로 신청 진입점으로 씁니다.

- **블록 헤더:** 팀 이름 + 덕아웃 위치(예: `선공 (3루 덕아웃)`), 충원 현황(`4/11`)
- **슬롯 행:** 순번 · 포지션명 · 우측 값. 슬롯 구성과 순서는 경기 데이터를 따릅니다(§3 기본 프리셋 참고)
- **슬롯 상태 2종**

| 슬롯 상태 | 우측 값 | 조건 | 탭 동작 |
| --- | --- | --- | --- |
| 빈자리 | **"신청 가능"** (강조색 + chevron) | 해당 슬롯에 활성 예약 없음 | P-5로 이동, 이 포지션 프리필 |
| 신청됨 | **참가자 이름** | 활성 예약 존재 (RESERVED / PAYMENT_SUBMITTED / APPROVED) | 비활성 (탭 불가) |

- **이름은 신청 즉시 노출합니다.** 예약 상태(입금 전/승인 전/확정)를 슬롯에서 구분하지 않습니다. 실제 모집 공고가 그렇게 운영되고, 용병이 보드에서 알고 싶은 것은 "이 자리가 남아 있는가"이기 때문입니다. 본인 예약의 진행 상태는 P-8에서 확인합니다
- **표시하는 이름:** 본인이 잡은 슬롯은 닉네임, 대리 신청한 슬롯은 신청자가 입력한 참가자 이름입니다(§3.2)
- **노출 범위는 이름까지.** 급수·노쇼 이력은 노출하지 않습니다(§P-10 비공개 규칙 유지)
- **내 예약 슬롯:** 내 예약에 속한 슬롯은 **전부** `내 신청` 배지를 답니다. 대리로 잡아준 자리도 내가 취소·관리하는 대상이므로 본인 자리와 구분하지 않습니다
- **보드에는 금액을 넣지 않습니다.** 빈 슬롯의 우측은 "신청 가능"만 표시합니다. 보드가 답해야 하는 질문은 "이 자리가 남아 있는가" 하나이고, 11행마다 금액이 반복되면 그 질문이 흐려집니다. 금액은 상단 티어 요약(4줄)에서 한 번, 그리고 실제로 금액이 확정되는 P-5 선택 요약·P-6 입금액에서 다룹니다
- **전 슬롯 마감 시:** 두 팀의 모든 슬롯이 찼을 때만 경기 전체가 마감 처리됩니다. 한쪽 팀만 다 차면 나머지 팀은 계속 신청 가능

- **하단 버튼:** "신청하기" — 조건에 따라 분기. 여러 조건이 겹치면 아래 표기 순서대로 **위쪽 사유 하나만** 노출합니다
  1. `status ≠ OPEN` → "마감된 경기입니다"
  2. `is_suspended=true` → 버튼 비활성화 + "노쇼 누적으로 신청이 제한되었습니다" 안내 + **"문의하기"** 링크(§3.3 — 억울한 정지는 어드민이 해제)
     - 본인의 no_show_count는 노출하지 않고 정지 여부만 안내합니다 (카운트 수치는 마이페이지에서만)
  3. 이미 활성 예약 보유(중복/시간대 충돌) → 버튼 비활성화 + 사유 안내
  4. 빈 슬롯 0개 → 버튼 비활성화 + "모든 포지션이 마감됐어요"
  - 위 조건 모두 통과 시 활성화 → P-5 이동 (슬롯을 탭해서 들어오면 해당 포지션이 선택된 상태로 진입)
- **연동 API:** `GET /games/:gameId`

### P-5. 예약 신청 폼

- **입력 필드**
  - 희망 포지션 (필수, **다중 선택** — 팀 + 포지션 슬롯 1개 이상, §3.2)
    - P-4의 포지션 보드와 **같은 UI를 선택 가능 모드로** 재사용합니다. 정원 표시와 선택을 별개 요소로 나누지 않습니다
    - 선택은 **체크박스처럼 동작**합니다. 라디오가 아니므로 이미 고른 슬롯을 다시 탭하면 해제됩니다
    - 이미 찬 슬롯은 선택 불가 처리(비활성 + "마감" 표기)
    - P-4에서 빈 슬롯을 탭해 들어온 경우 해당 슬롯이 선택된 상태로 진입, 화면 안에서 추가·해제 가능
    - 전 슬롯 마감이면 이 화면에 진입할 수 없습니다(P-4에서 이미 차단)
    - **"무관" 값은 없습니다.** 포지션이 곧 정원 단위이므로 어느 슬롯을 점유할지 정하지 않은 신청은 성립하지 않습니다
    - 선공·후공을 **섞어서** 고를 수 있습니다(친구는 상대 팀에 넣는 경우). 팀 탭을 바꿔도 선택은 유지됩니다
  - 참가자 이름 (선택한 슬롯 수만큼, 각 필수 — 텍스트)
    - 슬롯을 고르면 아래 "참가자" 영역에 입력 행이 하나씩 생깁니다. 슬롯을 해제하면 해당 행도 사라집니다
    - **첫 슬롯은 본인 닉네임이 프리필**됩니다. 나머지는 빈 값이며 대리 신청하는 동행자의 이름을 적습니다
    - 여기 적은 이름이 P-4 포지션 보드에 그대로 노출됩니다(§P-4 노출 원칙)
  - 입금자명 (필수, 텍스트 — 기본값으로 닉네임 프리필, 수정 가능). 슬롯이 여러 개여도 **입금은 1건**이므로 입금자명도 1개입니다
- **선택 결과 요약:** 선택한 슬롯 수와 **참가비 합계**를 표시합니다 (예: `3자리 선택 · 34,000원`). 슬롯을 추가·해제할 때마다 합계가 갱신됩니다
  - 합계 = 선택한 슬롯들의 티어 금액 합. 0원 슬롯(포수)은 합계를 올리지 않습니다
- **제출 전 안내 문구:** "신청 후 24시간 내 미입금 시 자동 취소돼요" (예약 전체가 한 번에 만료됩니다 — §3.2)
- **제출:** `POST /games/:gameId/reservations`
- **성공:** P-6 (입금 안내)로 이동, `expiresAt` 값 수신
- **에러 케이스 → 화면 처리**

| API 에러 코드 | 화면 반응 |
| --- | --- |
| `GAME_NOT_OPEN` | 제출 실패 다이얼로그 + P-3로 복귀 |
| `USER_SUSPENDED` | 제출 실패 다이얼로그, 사유 안내 + "문의하기" 경로(§3.3) |
| `TIME_SLOT_CONFLICT` | "이미 같은 시간대에 신청한 경기가 있어요" + 해당 예약 바로가기 |
| `DUPLICATE_RESERVATION` | "이미 이 경기에 신청했어요" + P-8 바로가기 |
| `GAME_FULL` | "모든 포지션이 마감됐어요" + P-3 복귀 |
| `POSITION_TAKEN` | **"○○ 자리가 방금 마감됐어요"** — 마감된 슬롯만 선택 해제 + 비활성화, 나머지 선택과 입력값은 유지, 합계 재계산. 화면 유지 |
| `INSUFFICIENT_SLOTS` | 여러 슬롯 중 일부만 남은 경우 — "고른 3자리 중 1자리가 마감됐어요. 남은 2자리로 신청할까요?" 다이얼로그(계속/취소) |
| `VALIDATION_FAILED` | 슬롯 미선택, 참가자 이름 미입력 등 인라인 에러, 화면 유지 |

> **부분 실패는 전부 실패로 처리합니다.** 슬롯 3개 중 1개가 방금 찼다면 나머지 2개도 예약하지 않고 화면을 유지한 채 사용자에게 되묻습니다. 일부만 잡힌 채 넘어가면 "누구 자리가 빠졌는지" 사용자가 P-6에서야 알게 됩니다.

### P-6. 입금 안내

- **표시 정보:** 입금 은행/계좌/예금주(경기 데이터 기준), 입금 금액(**예약에 속한 전체 슬롯의 티어 참가비 합계**, §3.1·§3.2), 남은 시간 카운트다운(`expires_at` 기준)
  - **슬롯별 내역을 함께 펼칩니다** (예: `3루 · 야수 17,000원` / `유격 · 야수 17,000원` / `포수 · 무료 0원`). 같은 경기라도 슬롯마다 금액이 다르고 대리 신청이면 여러 건이 합쳐지므로, 합계만 보여주면 왜 이 금액인지 검산할 수 없습니다
  - 슬롯이 1개면 내역 없이 금액과 티어만 한 줄로 표기합니다
- **버튼:** "입금 완료했어요" → `PATCH /reservations/:id/payment-submitted`
  - 성공 → 화면 내 상태 배지가 "승인 대기중"으로 전환, 안내 문구 "주최자 승인을 기다리고 있어요"
  - 실패(`NOT_RESERVED`/`RESERVATION_EXPIRED`) → "신청이 만료되었어요" 다이얼로그 + P-3 복귀
- **만료 임박 상태:** 12시간/1시간 전에는 카운트다운 색상 강조(경고색)로 시각적 긴급성 부여 — 알림(P-11)과 동일 타이밍
- **취소 버튼:** RESERVED 상태에서만 노출, `PATCH /reservations/:id/cancel`

### P-7. 내 예약 목록

- **탭 구성:** 진행중(RESERVED, PAYMENT_SUBMITTED, APPROVED) / 완료(ATTENDED) / 종료·취소(EXPIRED, CANCELLED, REJECTED, NO_SHOW)
- **리스트 아이템:** 경기장명, 일시, 상태 배지, (ATTENDED인데 미평가 건은) "평가하기" 배지
- **빈 상태:** 탭별 안내 문구 ("아직 진행중인 예약이 없어요" 등)
- **연동 API:** `GET /reservations/me`
- **아이템 클릭:** P-8로 이동. 단 RESERVED 상태 아이템은 P-6(입금 안내)로 바로 이동

### P-8. 예약 상세

- **표시 정보:** 경기 정보 요약, **신청 슬롯 목록**, 상태 이력, 상태별 안내 문구
- **신청 슬롯 목록:** 예약에 속한 슬롯을 전부 행으로 나열합니다 — `팀 포지션 · 참가자 이름 · 금액`. 본인 슬롯에는 `나` 표시
  - 슬롯이 여러 개면 마지막에 합계 행을 둡니다
  - 주최자가 승인 시 다른 슬롯으로 옮긴 경우, 해당 행에 변경 전 포지션을 함께 적고 "주최자가 포지션을 조정했어요" 안내를 노출합니다
- **취소는 예약 전체 단위입니다(§3.2).** 슬롯 하나만 빼는 조작은 제공하지 않습니다. 목록 행에 개별 삭제 버튼을 두지 마세요 — 가능해 보이면 안 됩니다
- **상태별 배지/문구 매핑**

| 상태 | 배지 | 안내 문구 |
| --- | --- | --- |
| RESERVED | 입금 대기 | 입금 안내로 이동 가능 |
| PAYMENT_SUBMITTED | 승인 대기 | 주최자 확인 중 |
| APPROVED | 승인 완료 | 확정 슬롯 목록 + 경기 당일 안내 |
| EXPIRED | 기간 만료 | 24시간 내 미입금으로 자동 취소됨 |
| CANCELLED | 취소함 | 본인이 취소한 예약 |
| REJECTED | 거절됨 | 주최자가 거절한 예약 |
| ATTENDED | 참가 완료 | "평가하기" 버튼 노출 (미평가 시) |
| NO_SHOW | 노쇼 처리 | 안내 문구만 (누적 횟수는 비노출, 마이페이지에서만 본인 확인) |

- **취소 버튼:** RESERVED/PAYMENT_SUBMITTED 상태에서만 노출

### P-9. 평가 작성

- **진입 조건:** 본인 예약이 ATTENDED이고 아직 해당 경기에서 미평가 대상자가 남아있을 때
- **구성:** 같은 경기 ATTENDED 참가자 리스트, 각 인원별로
  - 매너 점수 (1~5)
  - 실력-프로필 일치도 (1~5)
  - 시간 준수 (1~5)
  - 베스트플레이어 투표 체크박스 — **최대 2명까지만 선택 가능**, 3번째 선택 시도 시 "베스트플레이어는 최대 2명까지 선택할 수 있어요" 토스트, 선택 불가 처리
- **본인 항목:** 리스트에서 제외 (자기 평가 금지)
- **제출:** 대상자별 개별 제출 또는 일괄 제출(UX 결정 필요 — §2 확인 필요 항목 참고)
- **완료 후:** 평가 완료 대상자는 리스트에서 "평가완료" 배지로 전환, 전원 평가 완료 시 P-9 재진입 시 "모든 참가자 평가를 완료했어요" 안내로 대체

### P-10. 마이페이지

- **표시/수정 가능 정보:** 닉네임, 활동 지역, 주 포지션, self_level, 게임원 URL (P-2와 동일 필드, 수정 가능)
- **본인 전용 표시:** 노쇼 누적 횟수(no_show_count), 정지 여부(is_suspended) — **타인에게는 비공개**이므로 이 화면 외 어디에도 노출하지 않음
- **정지 상태일 때:** 정지 안내 블록 + **"문의하기"** 버튼을 함께 노출합니다(§3.3)
  - 문구: "노쇼가 누적되어 신청이 제한된 상태예요. 잘못 처리된 것 같다면 문의해주세요."
  - 대리 신청 때문에 본인이 오지 않은 노쇼까지 본인에게 쌓일 수 있으므로, **이의 제기 경로가 화면에 반드시 있어야 합니다**
- **기타:** 로그아웃 버튼

### P-11. 알림함

- **리스트 아이템:** 알림 유형별 아이콘/문구(입금 임박 12h/1h, 승인, 거절, 노쇼 처리), 발생 시각, 읽음 여부
- **아이템 클릭:** 관련 예약(reservation_id 존재 시) → P-8로 이동, 읽음 처리(`is_read=true`)
- **빈 상태:** "새로운 알림이 없어요"

## 2. 확인이 필요한 항목 (설계 판단 필요)

> 아래는 화면설계서 작성 중 제 판단으로 임시 결정한 부분입니다. 실제 개발 전에 확인해주세요.

1. **P-9 평가 작성 제출 방식** — 대상자별 개별 제출 vs 전원 작성 후 일괄 제출. 위 문서는 어느 쪽이든 동작하게 서술했지만, UX 관점에서 하나로 확정 필요.
2. **참가비 0원 슬롯의 입금 흐름** — 포수처럼 참가비가 0원인 슬롯은 입금할 금액이 없습니다. 신청 즉시 승인 대기로 넘길지(P-6 건너뜀), 그래도 주최자 승인을 거칠지 확정 필요. §3.1에서 0원을 유효한 값으로 열어 뒀으므로 상태머신에서 정해야 합니다.
3. **포수 출전수당** — 실제 공고는 포수 참가 시 현금 1만원을 **지급**합니다(참가비 0원을 넘어 마이너스). 서비스가 이 정산까지 다룰지, 경기 안내 문구로만 남길지 미정. 현재 문서는 후자 전제입니다.
4. **슬롯 구성의 편집 가능 범위** — §3 기본 프리셋 11개를 주최자가 경기마다 추가/삭제/순서 변경할 수 있게 할지, 고정 프리셋만 허용할지. 후자면 P-4 보드 레이아웃을 고정 높이로 잡을 수 있습니다.
5. **예약 후 인원 추가** — 이미 신청한 사람이 나중에 동행자를 더 넣고 싶을 때. 현재는 `DUPLICATE_RESERVATION`으로 막혀 있어 취소 후 재신청뿐입니다. 기존 예약에 슬롯을 추가하는 API가 필요할지 미정.
6. **슬롯 단위 부분 취소** — §3.2에서 v1 범위 밖으로 뒀습니다. 동행자 1명만 빠지는 상황은 현실에서 자주 생기므로 v2 후보입니다.
7. **`Position` enum 정합성** — 프리셋이 투수를 `선발`/`구원`으로 나누고 `지타`를 포함합니다. 기존 enum이 이 값들을 갖고 있는지, 프로필용 주 포지션 목록과 슬롯용 목록을 같은 enum으로 쓸지 확인 필요.
8. **ERD/API 정합성** *(2026-08-03 — 작성자가 직접 검토 중)* — 정원 모델을 포지션 슬롯 단위(§3) + 예약 1건 다중 슬롯(§3.2)으로 확정하면서 아래가 서버와 함께 정리되어야 합니다.
   - **`reservation_slot` 테이블 신설**이 필요합니다. `reservation.desired_positions`(배열)를 단일 컬럼으로 접는 게 아니라, `reservation 1 : N reservation_slot` 관계로 바꿉니다
     - `reservation_slot`: `reservation_id`, `team`, `position`, `participant_name`, `is_owner`(신청자 본인 슬롯 여부), `fee_tier`, `fee`
     - `(game_id, team, position)`에 **유니크 제약** — 슬롯 중복 점유를 DB에서 막아야 합니다. 동시 신청이 정확히 여기서 충돌합니다
   - 슬롯 예약은 **한 트랜잭션에서 전부 성공하거나 전부 실패**해야 합니다(§P-5 부분 실패 규칙). 일부만 잡히면 안 됩니다
   - `game`에 팀별 슬롯 목록(순서 포함), 슬롯별 점유 상태 집계
   - 에러 코드 `POSITION_TAKEN`(선택 슬롯 중 일부가 점유됨 — **어느 슬롯인지 응답에 포함**) / `GAME_FULL`(양 팀 전 슬롯 마감). 이전 판의 `TEAM_FULL`은 폐기
   - `league`에 티어별 참가비 4종, `game`은 생성 시 이 값을 복사. 슬롯 응답에 `feeTier`와 `fee` 동봉(§3.1 — 클라이언트가 포지션명으로 티어를 추론하지 않음)
   - `GET /games/:gameId` 응답의 슬롯 구조: `{ position, feeTier, fee, occupied, participantName?, isMine }`. **이름은 활성 예약이 있으면 상태와 무관하게 내려줍니다**(§P-4 노출 원칙). `isMine`은 내 예약에 속한 슬롯 전체에 true
   - 노쇼·평가는 `is_owner=true` 슬롯 기준으로만 동작합니다(§3.2). 급수 검증은 제거됩니다(§3.3)
   - `is_suspended` **해제용 어드민 API**가 필요합니다(§3.3) — 용병 화면의 "문의하기"가 닿을 곳이 있어야 합니다
9. **~~"무관" 배정 시점~~** — 폐기. §3에서 `ANY` 값 자체를 없앴습니다.

> **해소된 항목**
>
> - 포지션 다중 선택 → §3.2에서 예약 1건 = 슬롯 N개로 확정(대리 신청 지원). "1지망/2지망" 방식은 채택하지 않음
> - P-4 신청 불가 사유 우선순위 → §P-4에 4단계 순서로 확정(급수 분기 제거 후)

> - 슬롯 이름 노출 범위 → 신청 즉시 노출로 확정(예약 상태 구분 없음)
> - 대리 신청 인원 상한 → §3.2에서 **상한 없음**으로 확정
> - 급수 제한 → §3.3에서 **폐지**. 권장 급수 표기·필터만 유지
> - 대리 신청으로 인한 억울한 노쇼 정지 → §3.3에서 **어드민 수동 해제**로 구제

## 3. 정원 모델 (포지션 슬롯 단위)

> **2026-08-02 재확정.** 같은 날 앞서 내렸던 "팀 단위 통일" 결정을 되돌립니다.
> 실제 게스트 모집 공고가 팀별 포지션 명단 형태로 운영되고 있고("초공 3루 덕아웃 — 1. 구원 / 2. 선발 / 3. 포수 …"), 용병이 신청할 때 가장 먼저 확인하는 정보가 "내 포지션이 비어 있는가"이기 때문입니다. 정원 단위를 포지션으로 되돌려 화면과 실제 운영을 일치시킵니다.

- 경기의 정원은 **팀 × 포지션 슬롯** 단위입니다. 선공 / 후공 두 팀이 각각 슬롯 목록을 가집니다.
- **슬롯 1개 = 정원 1명.** 한 슬롯은 활성 예약 1건만 점유할 수 있고, 점유된 슬롯은 다른 사람이 선택할 수 없습니다.
- 용병은 신청 시 **팀 + 포지션 슬롯을 하나만** 고릅니다. "무관" 값은 없습니다.
- 슬롯 점유는 **신청(RESERVED) 시점에 즉시** 발생합니다. 입금·승인을 기다리는 동안에도 자리는 잠겨 있고, 만료(EXPIRED)·취소(CANCELLED)·거절(REJECTED) 시 슬롯이 다시 열립니다.
- 경기 전체 마감(`GAME_FULL`)은 **양 팀의 모든 슬롯이 찼을 때만** 성립합니다.
- **기본 슬롯 프리셋 (팀당 11):** 선발 · 구원 · 포수 · 1루 · 2루 · 3루 · 유격 · 좌익 · 중견 · 우익 · 지타
  - 실제 슬롯 구성·개수·순서는 경기 데이터를 따릅니다. 프리셋은 주최자가 경기를 만들 때의 기본값입니다.
- 프로필의 주 포지션(P-2/P-10)은 **신청 시 기본 선택값을 제안하는 용도**로만 쓰입니다. 그 포지션으로만 신청할 수 있다는 제약은 없습니다.
- 화면별 반영 위치

| 화면 | 표기 |
| --- | --- |
| P-3 경기 목록 카드 | `선공 4/11 · 후공 6/11` + 빈 포지션 칩(최대 2개) |
| P-4 경기 상세 | 팀별 포지션 보드 2블록, 슬롯 상태 2종(빈자리=`신청 가능` / 신청됨=참가자 이름), 슬롯 단위 마감 |
| P-5 예약 신청 폼 | 포지션 보드 재사용, 슬롯 **다중 선택**(마감 슬롯 비활성) — §3.2 |
| P-8 예약 상세 | 신청 포지션 / 확정 포지션 |

### 3.1 참가비 — 포지션 티어 단위

> **2026-08-02 확정.** 경기당 단일 참가비에서 **티어별 참가비**로 변경합니다.

- 참가비는 **리그가 직접 정합니다.** 경기마다 임의로 정하는 값이 아니라 리그 설정을 따르고, 경기 생성 시 리그 값을 복사해 옵니다.
- 금액 구분 단위는 **포지션 티어 4종**입니다. 포지션 11개마다 금액을 따로 두지 않습니다.

| 티어 | 포함 포지션 | 예시 금액 |
| --- | --- | --- |
| `투수` | 선발, 구원 | 13,000원 |
| `포수` | 포수 | **무료** (0원인 경우가 일반적) |
| `야수` | 1루, 2루, 3루, 유격, 좌익, 중견, 우익 | 17,000원 |
| `지타` | 지타 | 13,000원 |

- **0원 허용.** 포수 무료가 관행이므로 0원이 유효한 값이며, 화면에는 `무료`로 표기합니다. 0원 슬롯은 P-6(입금 안내)를 건너뛰는지 여부를 서버와 맞춰야 합니다(§2 참고).
- 슬롯 → 티어 매핑은 **서버가 내려주는 값**을 씁니다. 클라이언트가 포지션명으로 티어를 추론하지 않습니다(리그마다 지타를 야수로 묶는 등 변형이 있을 수 있음).
- 화면별 반영 위치

| 화면 | 표기 |
| --- | --- |
| P-3 경기 목록 카드 | 최저가 기준 `13,000원부터` (티어 4개를 카드에 나열하지 않음) |
| P-4 경기 상세 | **상단 티어 4종 요약에서만.** 포지션 보드 행에는 금액을 넣지 않습니다 |
| P-5 예약 신청 폼 | 선택한 슬롯의 금액을 확정 금액으로 표시 (보드 하단 요약 행) |
| P-6 입금 안내 | 확정된 슬롯 금액을 입금 금액으로 사용 |

### 3.2 예약 1건 = 슬롯 N개 (대리 신청)

> **2026-08-02 확정.** 예약 1건이 슬롯 1개를 잡는 모델에서 **여러 슬롯을 잡는 모델**로 바꿉니다.

실제 모집에서는 **한 사람이 동행자 몫까지 함께 신청**합니다. 원본 공고에도 "팀참가 (15만원) 팀 신청 환영"이 있습니다. 1인 1슬롯으로 두면 친구 3명을 데려오는 사람이 계정을 3개 만들거나 신청을 3번 해야 합니다.

- **예약(reservation) 1건이 슬롯 1개 이상을 점유합니다.** 슬롯 1개 = 참가자 1명은 그대로입니다(§3).
- **슬롯마다 참가자 이름을 받습니다.** 첫 슬롯은 신청자 본인(닉네임 프리필), 나머지는 대리 신청 대상입니다.
  - 대리 신청 대상은 **계정이 없어도 됩니다.** 이름 문자열만 저장합니다.
- **선공·후공을 섞어서** 고를 수 있습니다.
- **참가비는 슬롯 티어 금액의 합계**입니다(§3.1). 입금은 예약 단위로 1건입니다.
- **상태는 예약 단위로 움직입니다.** 만료·취소·승인·거절은 예약에 속한 슬롯 전체에 동시에 적용됩니다. 슬롯 단위 부분 취소는 v1 범위 밖입니다(§2).
- **한 경기당 활성 예약은 여전히 1건입니다.** 여러 명을 신청하려면 한 번에 골라야 하고, 이미 예약이 있으면 `DUPLICATE_RESERVATION`으로 막습니다. "예약 후 인원 추가"는 §2 확인 항목입니다.
- 화면별 반영 위치

| 화면 | 표기 |
| --- | --- |
| P-4 경기 상세 | 슬롯마다 참가자 이름. 내 예약에 속한 슬롯은 전부 `내 신청` 배지 |
| P-5 예약 신청 폼 | 슬롯 다중 선택(체크박스) + 슬롯별 참가자 이름 입력 + 합계 |
| P-6 입금 안내 | 합계 금액 + 슬롯별 내역 |
| P-8 예약 상세 | 슬롯 목록(포지션 + 참가자 이름) |

#### 대리 신청이 건드리는 것들

| 항목 | 처리 |
| --- | --- |
| 대리 인원 수 | **상한 없음.** 한 예약이 슬롯 11개를 전부 잡아도 됩니다(팀 단위 신청이 실제로 있으므로) |
| 노쇼 카운트 | **신청자 본인 계정에만** 누적합니다. 동행자는 계정이 없으므로 데려온 사람이 책임집니다. 억울한 경우는 어드민이 해제합니다(§3.3) |
| 평가(P-9) | 계정이 있는 참가자만 평가 대상입니다. 이름만 있는 동행자는 리스트에서 제외 |
| 정지 검증 | 신청자 본인 기준으로만 검증합니다 |
| 급수 검증 | **없습니다.** §3.3에서 급수 제한 자체를 폐지했습니다 |

> 대리 신청을 열면 "본인이 아닌 사람 때문에 본인이 불이익을 받는" 경우가 생깁니다. 이를 규칙으로 막는 대신 **어드민 해제**로 사후 구제합니다(§3.3). 그래서 정지 안내가 뜨는 모든 자리(P-4·P-5·P-10)에 문의 경로를 함께 둡니다.

### 3.3 급수 제한 폐지 · 어드민 구제

> **2026-08-03 확정.** 급수에 의한 참가 제한을 없애고, 제재는 노쇼 정지 하나만 남깁니다.

#### 급수는 제한이 아니라 정보입니다

- 경기의 급수 값은 **권장 급수**입니다. 초과해도 신청을 막지 않습니다.
- 폐기: `LEVEL_NOT_ELIGIBLE` 에러, P-4의 "신청 가능 급수를 초과했어요" 분기, 서버의 `required_level` 검증
- 유지: 프로필 `self_level`(P-2·P-10), 경기 카드·상세의 권장 급수 표기, P-3 급수 필터
  - 필터와 표기는 **탐색 보조**로 남깁니다. "4급 이하 경기를 찾고 싶다"는 요구는 여전히 유효하고, 이건 제한이 아니라 취향입니다
- 근거: 대리 신청에 인원 상한이 없으므로(§3.2) 급수 검증은 신청자 1명분만 통과하면 나머지가 프리패스가 됩니다. 강제되지 않는 규칙을 강제하는 척 남겨두면 UI만 복잡해집니다

#### 제재는 노쇼 정지만, 구제는 어드민이

- 남는 제재는 `is_suspended`(노쇼 누적) 하나입니다.
- **정지 해제는 어드민이 수동으로 처리합니다.** 자동 해제 규칙(일정 기간 경과 등)은 두지 않습니다.
- 용병 화면의 책임은 **이의 제기 경로를 항상 함께 보여주는 것**까지입니다.

| 화면 | 정지 상태에서 보여줄 것 |
| --- | --- |
| P-4 경기 상세 | 신청 버튼 비활성 + 사유 + "문의하기" |
| P-5 예약 신청 폼 | `USER_SUSPENDED` 다이얼로그에 "문의하기" |
| P-10 마이페이지 | 정지 안내 블록 + "문의하기" 버튼 (노쇼 누적 횟수는 여기서만 노출) |

> **어드민 화면은 이 문서 범위 밖입니다.** 해제 기능이 실제로 있어야 위 문의 경로가 의미를 갖습니다 — 주최자/어드민 문서에서 다뤄야 합니다(§4).
